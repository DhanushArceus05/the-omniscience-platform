# OmniKnowledge Processing (Phase 7 Steps 3–8)

## Processing boundary

Knowledge upload remains a storage-only operation and creates a file in `UPLOADED`. An authenticated caller explicitly starts or retries processing with `POST /workspaces/:workspaceId/knowledge/:fileId/process`. The route resolves the workspace from the authenticated owner and returns only after processing has either completed or failed. Retrieval, chat/RAG integration, and search are outside this milestone.

## Pipeline and storage

1. `DocumentExtractionService` extracts PDF/DOCX/TXT text.
2. `KnowledgeChunkingService` splits on whitespace into 250-word chunks with a 50-word overlap (stride 200). Chunk text joins the source words with one space. Empty input produces zero chunks. PDF chunks include the distinct source `pageNumbers` represented in that chunk; other formats do not receive invented page metadata.
3. `KnowledgeChunksRepository` writes a staging generation in MongoDB. Its unique `{ workspaceId, fileId, generationId, chunkIndex }` index and deterministic generation-scoped document IDs make retries idempotent without overwriting the currently published generation. Startup creates the new index before removing the exact obsolete pre-generation unique index; no chunk documents are deleted by this index upgrade.
4. `KnowledgeEmbeddingService` uses the registered OpenAI `OmniProvider` and `text-embedding-3-small` in bounded batches (`KNOWLEDGE_EMBEDDING_BATCH_SIZE`, default 32, maximum 128). Every response index and 1536 finite vector coordinates are validated. `tokenEstimate` is `ceil(wordCount × 1.33)`, a heuristic rather than a tokenizer result.
5. `KnowledgeVectorsService` idempotently creates/validates the single `omniscience_knowledge` Qdrant collection (1536 dimensions, Cosine) and its workspace/file/generation/index payload indexes. Deterministic UUID point IDs include the generation. New-generation vectors are indexed without overwriting the active generation.
6. PostgreSQL atomically switches `activeGenerationId` and publishes `READY` only after MongoDB persistence, embedding, Qdrant indexing, and generation reconciliation succeed; `chunkCount` is switched with the generation.

## Status and recovery

The visible successful progression is `UPLOADED → PROCESSING → EXTRACTED → EMBEDDING_PENDING → READY`. Every processing claim receives an unpredictable UUID fencing token stored in `processingAttemptId`; all state transitions and guarded writes require that token. A replacement attempt fences the prior worker, which cannot publish or record failure for the new attempt. The processing token is also the staging `generationId`. Failed first processing records a fixed stage code; failed reprocessing retains the previous `activeGenerationId` and returns the file to `READY`. The explicit process route can retry failed files. A processing lease can be reclaimed after 30 minutes without a heartbeat.

Mongo and Qdrant writes are scoped to workspace, file, and generation. Each bounded persistence operation holds a PostgreSQL row lock while checking the current fencing token; a deletion claim takes the same row lock and moves the file to `DELETING`, so cleanup waits behind an in-flight write and prevents later writes. Provider calls do not hold a database transaction; the token is checked after each provider batch and before persistence. Reprocessing leaves the published generation untouched until an atomic PostgreSQL pointer switch. Failed/inactive generations are cleaned immediately when possible and retried by periodic reconciliation. A stale processing lease is conditionally fenced by reconciliation or the next processing claim; the old generation is then inactive and safe to clean. A crash can leave staging artifacts, but cannot publish them; subsequent retries and reconciliation are idempotent.

File deletion first claims `DELETING` with a distinct lifecycle token. This prevents new read leases. Existing PostgreSQL-backed leases may finish and renew while pinned to their exact active generation; deletion waits for them to be released or expire before clearing workspace/file-scoped Qdrant and MongoDB generations, the local source, and PostgreSQL metadata. Lease expiry creation, renewal, validation, and cleanup use PostgreSQL `clock_timestamp()`, not API-host clocks. A drain timeout fails deletion and leaves the file recoverable in `DELETING`; it never reports success while a valid lease remains. Lease TTL exceeds the configured provider request timeout, and leases heartbeat every 30 seconds. Non-streaming and streaming model execution receive the read-lease cancellation signal, which is forwarded to the provider adapter and SDK request. Anthropic passes the signal to its SDK request and retry loop; Gemini's SDK uses `abortSignal` to abort the client request, but explicitly cannot guarantee cancellation of model work already accepted by Google's service. No client can recall a prompt already delivered to a remote provider. A process crash is recovered after lease expiry; this is bounded local recovery, not proof that a remote provider stopped processing. Generation publication waits for old-generation readers to drain before atomically switching the active pointer. Readers never switch generations mid-request. Failed cleanup releases the deletion token but retains `DELETING` metadata so an authorized retry can safely resume; processing cannot restart while deletion is pending.

Account deletion marks every KnowledgeFile owned by the account `DELETING` under PostgreSQL row locks, then drains all account leases before allowing the existing user/workspace cascades. A timeout leaves the account present and the files fenced in `DELETING`; a repeat attempt can safely reclaim the lifecycle claims and retry. The lease FK remains `RESTRICT`, so an unexpected path that bypasses this orchestration fails closed. There is currently no direct workspace-delete endpoint; any future workspace cascade must call the corresponding prepare-and-drain methods before deleting workspace metadata. A six-hour reconciliation pass confirms workspace/file state in PostgreSQL before removing orphaned workspaces or inactive generations, and skips generations with live leases. Local source files continue to use the Step 1 storage reconciliation/grace period.

## Step 6 — Retrieval

`KnowledgeRetrievalService` accepts the authenticated owner ID, server-authorized workspace ID, and bounded query. It verifies ownership with `WorkspacesService`, loads only `READY` KnowledgeFile rows with an active generation, and embeds the query through `KnowledgeEmbeddingService` using the fixed `text-embedding-3-small` model (1536 finite dimensions). Qdrant receives a mandatory server-built filter containing the workspace ID and the active generation IDs from those authoritative PostgreSQL rows; no filter is accepted from a client.

The server validates every Qdrant hit, including its deterministic point ID and payload. It then rechecks `READY`/active-generation metadata and loads Mongo chunks by workspace, file, generation, and chunk ID. Missing, stale, duplicate, malformed, or cross-workspace results are discarded. Retrieval result order is deterministic (score descending, then file and chunk), bounded by configuration, and optionally diversified per file.

Defaults are `KNOWLEDGE_RETRIEVAL_LIMIT=8` (maximum 20), `KNOWLEDGE_RETRIEVAL_MIN_SCORE=0.35` (Cosine score range -1 to 1), and `KNOWLEDGE_RETRIEVAL_PER_FILE_LIMIT=3` (maximum 10). Search overfetch is capped at 64 Qdrant points. These values are server configuration, not request fields.

## Step 7 — Assistant RAG integration

The existing authenticated send and stream endpoints accept an optional `useKnowledge: true` flag. The web chat composer exposes the same explicit per-message toggle. The default is false and preserves the original prompt and provider path. This is workspace-level retrieval; clients cannot choose file IDs or supply prompt fragments.

For an enabled turn, the conversation must first resolve to the authenticated owner's workspace-scoped conversation. The user message is persisted with `knowledgeRequested` before retrieval, matching the existing persistence contract. A client-generated UUID `requestId` is stable across retries; Mongo persists it with the owner/workspace/conversation and user turn, with a unique user-turn index. A retry with the same key and content reuses that user message and uses an expiring conditional attempt lease. Concurrent retries cannot claim the same live attempt. Assistant attempts are stored under their unique fencing token as hidden staged records; one conditional update of the user turn atomically records the winning assistant ID and marks the request completed. A stale attempt cannot publish by passing an earlier lease check, and staged/incomplete attempts are excluded from message reads. Only the assistant ID referenced by the user-turn publication pointer is replayed. Reusing the key with different content or Knowledge toggle is rejected. Retrieval failures fail closed with a safe service error: no assistant message is generated and no source is claimed. For streaming, `start` explicitly sets `assistantExpected:false`, then terminal `error`; the frontend keeps the user bubble, creates no assistant placeholder, clears loading, and retry reuses the same key. Partial stream content is persisted as an incomplete attempt artifact, leaves the request retryable, and is never replayed as a completed `done` response. With no READY files or no useful hits, the original question goes to the existing OmniCore pipeline unchanged and the saved assistant message is marked `NOT_GROUNDED` with no citations.

`KnowledgeContextService` adds deterministic `[S1]` source labels and a bounded reference block (up to 8 excerpts, 1200 characters per excerpt, and 6000 total reference characters). It tells the model that quoted JSON excerpts are untrusted evidence, not instructions, and to ignore embedded commands, avoid unsupported facts, and cite only provided labels. The original question is preserved. Retrieved text is never logged by this component.

Streaming remains on the existing SSE protocol (`start`, `delta`, `done`, `error`). Source labels are allowed only if present in the current retrieval set; unknown labels are stripped. The final `done` event carries the persisted assistant `Message`, including its optional attribution object. If retrieval fails after the user message is persisted, the stream emits `start` with `assistantExpected:false` and that user message followed by a terminal safe `error` event; no assistant generation runs and no assistant message is created. Mid-stream failures retain the established partial/incomplete response behavior.

## Step 8 — Citations and grounding

Assistant messages may carry an additive `knowledge` object containing `grounding` and `citations`. A citation includes its stable chunk-based ID, validated `[S#]` reference, file ID/name, chunk ID/index, genuine page numbers when present, retrieval score, and a short excerpt from the stored chunk. User messages never receive citation metadata. Existing Mongo messages without this field remain unchanged; no Prisma migration is needed for this message contract.

Before persisting attribution, the server validates source labels against the exact retrieval results, then rechecks workspace ownership, `READY` status, active generation, and the corresponding Mongo chunk. Unknown labels are removed from the final answer and do not produce citations. Duplicate citations are removed and ordering follows the deterministic retrieval order. Storage keys and disk paths are not returned.

Grounding is deliberately conservative and distinguishes reference from entailment. `NO_KNOWLEDGE` means retrieval was not enabled. `NOT_GROUNDED` means no validated source reference was attached. `SOURCE_REFERENCED` means at least one server-assigned label mapped to an actual retrieved and revalidated source; it does not mean the source supports any claim. `RETRIEVAL_UNAVAILABLE` means retrieval/revalidation could not be completed. Legacy `GROUNDED` and `PARTIALLY_GROUNDED` values remain readable for old persisted messages but are never emitted by new responses. No claim-entailment verifier exists, so source labels and similarity never establish truth or factual confidence. Citations use a clearly identified general excerpt selected from the stored chunk; model-generated quotations, filenames, file IDs, page numbers, excerpts, and URLs are not used as citation metadata. A valid source reference still does not prove the associated sentence is supported.

There is no cross-database transaction between PostgreSQL, MongoDB, Qdrant, and conversation persistence. PostgreSQL read leases coordinate multiple API instances, pin each read to one generation, block new readers after `DELETING`, and make deletion/generation publication wait for existing readers. Lease storage is in the new `knowledge_file_read_leases` table; its migration must be applied through the normal deployment process before this code is deployed. A process crash is recovered by lease expiration after the bounded provider timeout. If a remote model request has already been accepted, it cannot be recalled; the service keeps its lease until the request finishes or times out. Retrieval infrastructure failures are not converted into successful grounded answers. A failure after the user message is written leaves that user message visible and does not create an assistant reply; retry reuses that same logical turn.

## Operational limits

- OpenAI credentials are optional at API startup; processing fails safely until `OPENAI_API_KEY` is configured.
- MongoDB and Qdrant must be reachable for processing. Qdrant collection initialization is idempotent; an unavailable vector store does not make a KnowledgeFile `READY`.
- Processing runs synchronously in the authenticated request. There is no durable queue or automatic retry scheduler for failed files; a caller must retry through the process route. Per-call provider/Qdrant timeouts and the 30-minute processing lease bound individual waits, but there is no aggregate request deadline or document/chunk-count cap; large files may exceed proxy timeouts and may need a future worker/queue before production deployment.
- No arbitrary client-defined Qdrant filters are exposed. Retrieval is called only by the existing protected conversation pipeline.
- Retrieval and RAG unit/E2E tests use mocked providers, Qdrant HTTP, Prisma, and MongoDB helpers. They verify the real Nest route, ownership guards, query/filter construction, generation checks, prompt bounds, and citation persistence, but no live MongoDB/Qdrant integration or OpenAI request is made by the checks.
- No Step 9 Knowledge management frontend is included; the only UI change is the per-message Knowledge toggle in the existing chat composer.
